# Экспорт старого сайта WordPress → новый сайт на Astro

Эта инструкция для владельца сайта (macOS, без опыта программирования). Инструмент лежит в `tools/wp-export/`
и **запускается только у вас на компьютере**: он берёт копию старого WordPress-сайта (дамп базы + папку `wp-content`)
и превращает её в файлы для нового сайта: страницы и новости в Markdown, картинки, таблицу редиректов,
отчёт-аудит и материалы для переноса дизайна.

> ⚠️ **Репозиторий публичный.** Дамп базы, `wp-config.php`, пароли, e-mail адреса и список пользователей в него попадать не должны.
> Инструмент их не выгружает и в конце сам проверяет результат, но дамп всегда держите **вне** папки репозитория (см. ниже).

## 1. Что нужно установить

1. **Node.js 20 или новее.** Зайдите на <https://nodejs.org>, скачайте версию **LTS** (кнопка слева), установите как обычную программу.
   Проверка: откройте программу **Терминал** (Cmd+Пробел → «Терминал») и введите `node -v` — должно показать `v20…` или больше.
2. **Копия этого репозитория** на вашем компьютере. Самый простой путь — программа [GitHub Desktop](https://desktop.github.com):
   «File → Clone repository → `tulubyev/kendo-baikal`». Либо в Терминале:
   ```bash
   git clone https://github.com/tulubyev/kendo-baikal.git ~/kendo-baikal
   ```
   Дальше в инструкции репозиторий лежит в `~/kendo-baikal` (папка «kendo-baikal» в вашей домашней папке).
3. Больше ничего ставить не нужно — у инструмента нет внешних зависимостей (`npm install` не требуется).

## 2. Как получить копию старого сайта

Создайте **приватную** папку вне репозитория, например `~/kendo-private/`, и положите в неё:

### 2.1. SQL-дамп базы данных (файл `dump.sql`)

Сайт хостится на Beget, поэтому проще всего через phpMyAdmin:

1. Панель управления Beget → **MySQL** → у нужной базы кнопка **phpMyAdmin** (откроется в новой вкладке).
2. Слева выберите базу сайта → вверху вкладка **Экспорт** → метод **Быстрый**, формат **SQL** → **Вперёд**.
3. Скачанный файл переименуйте в `dump.sql` и положите в `~/kendo-private/`.

(Подойдёт и архив `dump.sql.gz` — инструмент читает его без распаковки. Если на сайте очень много данных, лучше сжатие gzip.)

### 2.2. Папка `wp-content`

1. Панель Beget → **Файловый менеджер** (или FTP-клиент, например Cyberduck) → папка сайта (`kendo-baikal.ru/public_html`).
2. Скачайте папку **`wp-content`** целиком (в ней важны `uploads` — картинки и файлы, и `themes` — тема оформления).
   В файловом менеджере удобнее сначала «Архивировать», потом скачать один zip-файл и распаковать его на Mac.
3. Положите её как `~/kendo-private/wp-content`. Папки `plugins`, `cache`, `upgrade` можно удалить — они не нужны и весят много.

Итог:
```
~/kendo-private/
├── dump.sql
└── wp-content/
    ├── uploads/
    └── themes/
```

### 2.3. Запасной вариант без дампа (по желанию)

Если дамп получить не получается: в админке WordPress → **Инструменты → Экспорт → Все содержимое** → скачать XML-файл
и запускать с `--wxr export.xml` вместо `--sql`. Этот вариант беднее: в нём нет списка плагинов и настроек темы,
поэтому отчёт и дизайн получатся неполными. Основной путь — дамп.

## 3. Запуск

В Терминале:

```bash
cd ~/kendo-baikal
node tools/wp-export/bin/export.mjs \
  --sql ~/kendo-private/dump.sql \
  --wp-content ~/kendo-private/wp-content \
  --site-url https://kendo-baikal.ru \
  --out ~/kendo-private/export-output
```

(Знак `\` в конце строки — просто перенос; можно ввести всё одной строкой.)

Что будет в Терминале: шаги ①–④ и итоговая строка «Готово». Работа занимает от секунд до пары минут.
Результат кладётся в `--out` — **рекомендуем тоже вне репозитория**, как в примере. Папка вывода при каждом запуске
перезаписывается (только внутри неё), так что запускать можно сколько угодно раз.

### Дополнительные параметры

| Параметр | Что делает |
|---|---|
| `--wxr файл.xml` | вход из экспорта WordPress вместо SQL-дампа (запасной вариант) |
| `--slug-mode keep` | оставлять кириллицу в адресах страниц (по умолчанию — транслитерация: `Первый турнир` → `pervyy-turnir`) |
| `--prefix wp_` | если в дампе несколько сайтов/наборов таблиц — выбрать префикс |
| `--max-image-mb 0.5` | порог предупреждения о «тяжёлых» файлах (по умолчанию 1 МБ) |
| `--allow-email club@kendo-baikal.ru` | подтвердить, что этот e-mail — публичный контакт клуба (можно `@kendo-baikal.ru` — весь домен; параметр можно повторять) |
| `--screenshots-from https://kendo-baikal.ru` | сделать скриншоты старого сайта, см. раздел 7 |
| `--quiet` | меньше сообщений |

Справка: `node tools/wp-export/bin/export.mjs --help`.

## 4. Что получится на выходе

```
export-output/
├── content/
│   ├── pages/             ← страницы: index.md (главная), klub.md, klub/istoriya.md …
│   └── posts/             ← новости: <slug>.md
├── public/
│   └── uploads/           ← только реально используемые картинки и файлы (миниатюры -300x200 пропущены)
├── design-import/         ← материалы для переноса дизайна
│   ├── tokens.json        ← цвета, шрифты, размеры, радиусы, ширина контейнера
│   ├── templates.md/json  ← структура шаблонов темы (шапка, подвал, главная, запись, страница)
│   ├── menu.json          ← главное меню (дерево, уже с новыми адресами)
│   ├── theme/<тема>/      ← CSS темы, шрифты, нужные картинки (PHP не копируется)
│   ├── branding/          ← логотип, иконка сайта, favicon
│   └── screenshots/       ← скриншоты старого сайта (если запускали с --screenshots-from)
├── redirects.csv          ← старые адреса → новые (301)
├── report.md              ← отчёт-аудит (читать глазами)
└── report.json            ← то же самое для машин
```

Формат Markdown-файлов — строго по контракту из [`PLAN.md`](PLAN.md):

* **Страницы** (`/<slug>/`, вложенные — в подпапках; `index.md` — главная): `title`, `description`, `menu`/`order` (для пунктов главного меню верхнего уровня), `image` (обложка страницы).
* **Новости** (`/news/<slug>/`): `title`, `description`, `date`, `updated`, `category`, `tags`, `cover`.
* Имя файла = slug. Черновиков в выгрузке нет, поэтому поле `draft` не пишется (по умолчанию `false`).
* Картинки и файлы в тексте переписаны на `/uploads/…`, внутренние ссылки — на новые адреса.

## 5. Что и куда копировать

Из папки вывода — в корень репозитория (`~/kendo-baikal`), **только эти пять вещей**:

```bash
OUT=~/kendo-private/export-output
cd ~/kendo-baikal

mkdir -p src/content public
cp -R "$OUT/content/pages"  src/content/pages
cp -R "$OUT/content/posts"  src/content/posts
cp -R "$OUT/public/uploads" public/uploads
cp -R "$OUT/design-import"  design-import
cp    "$OUT/redirects.csv"  redirects.csv
```

(Если папки `src/content/pages` или `src/content/posts` уже есть с заглушками — удалите их перед копированием,
иначе `cp -R` положит новую папку внутрь старой.)

## 6. Отчёт и проверки

Откройте `export-output/report.md` (двойной клик → в любом текстовом редакторе, или `open ~/kendo-private/export-output/report.md`).
В нём:

* сколько страниц, записей и файлов; типы записей; черновики/приватные записи (списком, **без содержимого**);
* **активные плагины** и что каждый значит для Astro (формы, галереи, календари, SEO, слайдеры, магазин…);
* дерево меню, найденные формы, внешние встраивания (YouTube, карты…), шорткоды, которые не удалось перенести;
* битые и внешние ссылки (инструмент работает без интернета и внешние ссылки не проверяет, а только перечисляет);
* тяжёлые файлы (> 1 МБ) и файлы, которые упоминаются в тексте, но не найдены в `uploads`;
* раздел **«Требует ручного внимания»** — страницы, которые стоит просмотреть глазами. В самих Markdown-файлах
  такие места помечены комментариями `<!-- TODO(wp-export): … -->`.

**Самопроверка секретов.** В конце инструмент сканирует весь вывод. В Терминале вы увидите:

* `✔ проверка на секреты и e-mail пройдена` — всё хорошо;
* `⚠️ В ТЕКСТЕ НАЙДЕНЫ E-MAIL АДРЕСА` (код выхода 4) — файлы всё равно записаны, но коммитить нельзя, пока вы не решите:
  это публичный контакт клуба (тогда запустите ещё раз с `--allow-email адрес`) или адрес нужно убрать из текста;
* `🛑 НАЙДЕНЫ СЕКРЕТЫ` (код выхода 3) — в выводе есть хэш пароля, ключи/соли из `wp-config.php` или e-mail пользователя WordPress.
  **Ничего не коммитьте**, сообщите разработчику.

## 7. Скриншоты старого сайта (необязательно)

Нужны для сравнения дизайна. Один раз установите Playwright (внутри папки инструмента):

```bash
cd ~/kendo-baikal/tools/wp-export
npm install playwright
npx playwright install chromium
```

И добавьте к команде запуска `--screenshots-from https://kendo-baikal.ru` (можно указать и локальную копию сайта,
например `http://localhost:8080`). Появится `design-import/screenshots/` — главная, страницы из меню и последняя новость
в ширинах 1440 (desktop) и 390 (mobile). Если Playwright не установлен или сайт недоступен — будет предупреждение,
остальной экспорт не пострадает.

## 8. Что НЕЛЬЗЯ коммитить

* `dump.sql`, `*.sql`, `*.sql.gz` (они в `.gitignore`, но проверяйте `git status`);
* `wp-config.php`, любые файлы `.env`, пароли и ключи;
* папку `wp-content` целиком, `plugins`, резервные копии;
* `report.md` / `report.json` (в них список черновиков и служебная информация — отчёт для вас);
* всё, что находится в `~/kendo-private/`, кроме пяти вещей из раздела 5;
* выгрузки пользователей и комментариев (инструмент их не создаёт — но если сделали вручную, тоже не коммитьте).

Перед коммитом посмотрите `git status` — в списке должны быть только `src/content/…`, `public/uploads/…`, `design-import/…`, `redirects.csv`.

## 9. Как отправить результат

Вариант А — через Терминал:

```bash
cd ~/kendo-baikal
git checkout -b content-import
git add src/content public/uploads design-import redirects.csv
git status          # убедитесь, что нет ничего лишнего (дампов, wp-config, отчётов)
git commit -m "Импорт контента и материалов дизайна из WordPress"
git push -u origin content-import
```
Затем на GitHub откройте предложенный «Compare & pull request» и создайте pull request.

Вариант Б — через GitHub Desktop: создайте ветку, отметьте изменённые файлы (только из списка выше), «Commit», «Publish branch», «Create Pull Request».

Вариант В (если Git вызывает затруднения): заархивируйте в zip пять элементов из раздела 5 и передайте их разработчику
**через защищённый канал** (не публикуя в открытом доступе).

## 10. Что инструмент делает и чего не делает

**Делает**

* Разбирает дамп потоково, без установки MySQL (поддерживает `.sql` и `.sql.gz`, учитывает префикс таблиц, экранирование, большие файлы).
* Берёт только опубликованные страницы и записи; ревизии, черновики, приватные и защищённые паролем записи, корзину пропускает.
* Не читает пользователей и комментарии (e-mail пользователей из дампа запоминаются только в памяти — чтобы проверить, что их нет в результате).
* Конвертирует классический редактор, блоки Gutenberg и основные шорткоды (`[caption]`, `[gallery]`, `[embed]`, `[video]`, повторно используемые блоки) в чистый Markdown;
  YouTube/Vimeo-ссылки превращает во встраиваемый `<iframe>`.
* Строит `redirects.csv` по структуре постоянных ссылок WordPress (в т. ч. `/?p=ID`, `/?page_id=ID`, рубрики и метки → `/news/`, файлы `/wp-content/uploads/…` → `/uploads/…`).
  Адреса записаны в процентном кодировании, как их видит nginx (`/%D0%BA…`).

**Известные ограничения**

* **Формы** (Contact Form 7 и др.), слайдеры, календари событий, магазин и страницы конструкторов (Elementor, WPBakery…) автоматически не переносятся —
  они перечислены в отчёте и помечены `TODO` в тексте.
* Нестандартные типы записей (события, товары, портфолио) не экспортируются, только перечисляются в отчёте.
* Главное меню берётся по расположению `primary/main/header`; в `menu.json` попадает одно меню (остальные перечислены в отчёте).
  В `menu: true` помечаются страницы — пункты меню верхнего уровня.
* Структура ссылок с `%author%` не поддерживается для автоматических редиректов (остаются `/?p=ID`).
* Сложные таблицы (с объединением ячеек) упрощаются; проверьте их по пометке в отчёте.
* Токены дизайна (`tokens.json`) — эвристика по CSS; значения нужно проверять глазами, а не использовать вслепую.
* Внешние ссылки не проверяются на доступность (инструмент работает без интернета).
* Если в WordPress было несколько страниц с одинаковым адресом или адрес совпал с зарезервированным (`news`, `admin`, `uploads`),
  он автоматически получит суффикс (`-2`, `-page`) — смотрите раздел «Изменённые адреса» в отчёте.

## 11. Если что-то пошло не так

| Сообщение | Что делать |
|---|---|
| `node: command not found` | Node.js не установлен или Терминал открыт до установки — закройте и откройте заново |
| `Файл не найден: …` | Проверьте путь; можно перетащить файл из Finder в окно Терминала — путь вставится сам |
| `В дампе не найдены таблицы WordPress` | Выгружена не та база, или у таблиц другой префикс — укажите `--prefix` |
| В отчёте «Папка `wp-content/uploads` не найдена» | Вы указали неверную папку в `--wp-content` |
| `Тема … не найдена в wp-content/themes` | Скачайте папку темы (она названа в отчёте) |

## 12. Для разработчиков

```bash
cd tools/wp-export
npm test                # тесты на синтетических фикстурах (без реальных данных)
npm run fixture         # создать пробную «копию WordPress» в tools/wp-export/.fixture (команда запуска будет выведена)
```

Структура: `src/sql.mjs` (потоковый разбор mysqldump), `wpdata.mjs`/`wxr.mjs` (модель), `content.mjs` + `html2md.mjs`
(Gutenberg/шорткоды → Markdown), `site.mjs` (slug-и, пути, меню, старые URL), `media.mjs`, `links.mjs`, `redirects.mjs`,
`design.mjs` + `css.mjs` (дизайн-токены), `report.mjs`, `secrets.mjs`, `validate.mjs` (проверка frontmatter по контракту).
