# Админка сайта kendo-baikal.ru

Админка — это страница **https://kendo-baikal.ru/admin/**. Через неё редакторы добавляют новости и правят страницы, не трогая код. Сервера и базы данных у админки нет: каждое сохранение — это обычный коммит в репозиторий `tulubyev/kendo-baikal` на GitHub, после чего сайт пересобирается автоматически.

## Почему Sveltia CMS (для разработчиков)

| | |
|---|---|
| Выбор | **Sveltia CMS 0.229.0** (npm `@sveltia/cms`), формат `config.yml` совместим с Decap CMS |
| Почему | Статический SPA: 0 МБ памяти на VPS, русская локаль (`locale: ru`), транслитерация кириллицы в slug, поддержка редакционного процесса через pull request'ы |
| Вход | **Кнопка «Войти через GitHub»** → всплывающее окно `https://kendo-baikal.ru/oauth/auth` → GitHub → `/oauth/callback`. Это наш мини-прокси `oauth/` (Node.js без зависимостей, контейнер ≤ 48 МБ, [`oauth/README.md`](../oauth/README.md)): проверяет логин по списку `ALLOWED_USERS` и только тогда отдаёт токен. **Запасной вариант — вход по персональному токену** (кнопка остаётся, `auth_methods` не задан) |
| Scope | `public_repo` (`auth_scope` в `config.yml`): коммиты, pull request'ы и метки в публичном репозитории. Sveltia по умолчанию просит `repo` (доступ и к приватным репозиториям) — для публичного репозитория это лишнее. Если репозиторий станет приватным — поставьте `repo` и в `config.yml`, и в `OAUTH_SCOPE` прокси |
| Режим публикации | **`publish_mode: editorial_workflow`**: каждая правка — отдельная ветка `cms/<коллекция>/<адрес>` и pull request с меткой статуса (`sveltia-cms/draft` → `sveltia-cms/pending_review` → `sveltia-cms/pending_publish`). «Опубликовать» сливает PR в `main` (squash). Одобрение владельца обеспечивает **защита ветки `main` в GitHub** (см. «Для владельца»), а не сама админка |
| Версия | Закреплена в `public/admin/index.html` (`unpkg.com/@sveltia/cms@0.229.0/...`) + SRI-хэш `integrity`: подмена файла на CDN не пройдёт. Локали и вспомогательные чанки CMS сама подтягивает с unpkg (версия та же) — поэтому в CSP `/admin/` разрешён `unpkg.com`, остальной сайт ничего внешнего не грузит |

Окно входа открывается на том же сайте (`/oauth/…` обслуживает Traefik, не nginx), поэтому CSP `/admin/` менять не пришлось: запросы CMS идут на `api.github.com` (REST и GraphQL), он уже разрешён.

Поля коллекций строго соответствуют контракту frontmatter из `docs/PLAN.md` и схемам `src/content.config.ts`. **Если меняете поля — меняйте и схему Astro, и `public/admin/config.yml` одновременно.**

### Обновление CMS

```bash
npm view @sveltia/cms version                       # новая версия
npm pack @sveltia/cms@X.Y.Z && tar xzf sveltia-cms-X.Y.Z.tgz
echo sha384-$(openssl dgst -sha384 -binary package/dist/sveltia-cms.js | openssl base64 -A)
```
Подставьте версию и хэш в `public/admin/index.html`, проверьте вход и создание тестовой записи.

## Для редакторов

### 1. Как получить доступ и войти

1. Скажите владельцу сайта своё имя пользователя на GitHub (зарегистрироваться на github.com бесплатно; включите двухфакторную защиту — Settings → Password and authentication).
2. Владелец пригласит вас в репозиторий и добавит в список редакторов. Вам придёт письмо — нажмите **Accept invitation**.
3. Откройте https://kendo-baikal.ru/admin/ и нажмите **«Войти через GitHub»**. Откроется маленькое окно GitHub. При первом входе GitHub спросит разрешение для приложения сайта — нажмите **Authorize**. Окно закроется само, и вы окажетесь в админке. Всплывающее окно не открылось — разрешите всплывающие окна для сайта kendo-baikal.ru.

Если вместо входа вы видите «Доступ запрещён» — вашего логина ещё нет в списке редакторов: напишите владельцу.

**Запасной вход — по токену** (если кнопка GitHub не работает). Токен создаётся один раз:
   - GitHub → ваш аватар → **Settings** → **Developer settings** → **Personal access tokens** → **Fine-grained tokens** → **Generate new token**.
   - *Resource owner* — владелец репозитория (`tulubyev`); *Repository access* — **Only select repositories** → `kendo-baikal`.
   - *Permissions* → *Repository permissions* → **Contents: Read and write** и **Pull requests: Read and write** (второе нужно для отправки правок на проверку; без него сохранение упрётся в ошибку).
   - Срок действия — на ваше усмотрение (например, 1 год). Скопируйте токен (`github_pat_…`) — повторно он не показывается.
   - В админке нажмите **Sign in with GitHub using Token** (вход по токену) и вставьте токен.

Токен и вход через GitHub — это ваш пароль от сайта. Никому не показывайте. Если токен потерян или показан кому-то — отзовите его на GitHub (Settings → Developer settings → Personal access tokens) и создайте новый. Выйти из админки — меню профиля → **Выйти**.

### 2. Как создать новость (пост)

1. В админке слева выберите **Новости (записи)** → кнопка **Создать**.
2. Заполните: **Заголовок** и **Дату публикации** (обязательно), по желанию — краткое описание, рубрику, метки, обложку.
3. В поле **Текст записи** напишите текст. Кнопки над полем — заголовки, списки, ссылки, картинки.
4. Если запись ещё не готова — включите переключатель **Черновик**. Черновик не появится на сайте.
5. Нажмите **Сохранить**. Запись сохранится как **черновик правок** — на сайте её ещё нет (см. раздел «Как отправить на проверку»). Адрес записи создаётся из заголовка автоматически (русские буквы превращаются в латинские): `/news/<адрес>/`.

### 3. Как отправить правки на проверку

Правки редакторов попадают на сайт **только после одобрения владельца**. У каждой записи есть статус:

| Статус | Что значит |
|---|---|
| **Черновик** | Вы сохранили запись, но ещё работаете над ней. Видите только вы и владелец |
| **На рассмотрении** | Вы закончили и отправили на проверку. Владелец получит уведомление от GitHub |
| **Готово** | Владелец проверил и одобрил. Следующий шаг — публикация |

Как это выглядит:
1. Создайте или откройте запись, внесите правки, нажмите **Сохранить**. Запись появится в разделе **Редакционный процесс** (Workflow) в колонке «Черновики».
2. Когда всё готово, нажмите **«Отправить на рассмотрение»** (или перетащите карточку в колонку «На рассмотрении», или смените статус в меню записи).
3. Дальше — ждите. На сайте ничего не изменится, пока владелец не одобрит и не опубликует. Если нужно что-то поправить, владелец напишет вам; вернитесь в запись, исправьте и снова отправьте на рассмотрение.
4. После публикации карточка пропадёт из «Редакционного процесса», а сайт обновится через 3–6 минут.

Кнопку **«Опубликовать»** в админке у вас нажимать не нужно: пока владелец не одобрил, GitHub всё равно откажет («Не удалось опубликовать запись»). Это нормально, а не поломка.

Не путайте два «черновика»: **статус «Черновик»** — этап проверки (запись ещё не отправлена), а переключатель **«Черновик»** в самой записи (п. 6 ниже) прячет опубликованную запись с сайта.

### 4. Как загрузить картинку

- В поле **Обложка** (или кнопкой «картинка» в тексте) нажмите **Выбрать файл** → **Загрузить** и выберите файл с компьютера.
- Картинка сохранится в папку `/uploads/` в репозитории — вместе с записью, в одной проверке с ней (на сайте появится после публикации записи). Перед загрузкой уменьшите фото (достаточно ширины 1600 px и размера до 500 КБ — сайт быстрее, а репозиторий не раздувается).
- Имена файлов — латиницей, без пробелов. Одинаковые имена перезапишут друг друга.

### 5. Как править страницу

1. Слева выберите **Страницы** → найдите нужную в дереве (вложенность = адрес: `club/history` → `/club/history/`).
2. Измените текст/поля и сохраните.
3. **Показывать в главном меню** и **Порядок в меню** управляют верхним меню (меньше число — левее).
4. Главная страница — это страница `index`.

### 6. Как поставить черновик или снять с публикации

Включите переключатель **Черновик** в записи, сохраните и отправьте на рассмотрение — после публикации запись/страница исчезнет с сайта. Чтобы вернуть — выключите. Удалять ничего не обязательно.

### 7. Сколько ждать публикации

Публикация (слияние правок в основную версию) запускает автоматическую сборку и выкладку. Обычно сайт обновляется через **3–6 минут** после того, как владелец опубликовал запись. Сохранение черновика и отправка на рассмотрение сайт не меняют. Если сразу после сохранения ничего не изменилось — подождите и обновите страницу (Ctrl+F5).

### 8. Что делать при ошибке

| Что случилось | Что делать |
|---|---|
| Окно входа не открылось | Браузер заблокировал всплывающее окно — разрешите его для kendo-baikal.ru и нажмите кнопку снова |
| «Доступ запрещён» в окне входа | Вашего логина GitHub нет в списке редакторов — сообщите владельцу логин |
| «Ссылка для входа устарела» | Вход начат давно или окно открыли повторно — закройте его и нажмите «Войти через GitHub» заново |
| Не пускает при входе по токену / «Bad credentials» | Токен неверный, просрочен или отозван — создайте новый (п. 1) |
| «Not found» / нет прав сохранить | Вы не приняли приглашение в репозиторий или (при входе по токену) у токена нет прав **Contents** и **Pull requests: Read and write** на `kendo-baikal` |
| «Не удалось опубликовать запись» | Запись ещё не одобрена владельцем (так и задумано) или в ней есть ошибки в полях |
| Отправили на рассмотрение, а на сайте нет | Ждите одобрения владельца. Если прошло несколько дней — напомните ему |
| Опубликовано, но на сайте не появилось через 15 минут | Запись может быть с включённым переключателем **Черновик**. Иначе сообщите владельцу — возможно, упала сборка (вкладка **Actions** в репозитории) |
| Сохранение дало красную ошибку про поле | Проверьте обязательные поля (Заголовок, Дата) |
| Случайно испортили запись | Сообщите владельцу: любую версию можно вернуть из истории Git |
| Страница админки не открывается | Проверьте интернет; попробуйте другой браузер (Chrome/Firefox/Edge/Safari свежих версий); сообщите владельцу |

## Для владельца

Вход кнопкой GitHub состоит из трёх частей: **OAuth-приложение на GitHub** (даёт Client ID/Secret), **мини-прокси на VPS** (проверяет, что входящий — из списка редакторов) и **защита ветки `main`** (чтобы правки не попадали на сайт без вашего одобрения). Настраивается один раз, примерно за 20–30 минут. Порядок развёртывания на сервере — в [`DEPLOY.md`](../DEPLOY.md), раздел «OAuth-прокси админки».

### Шаг 1. Создайте OAuth-приложение на GitHub

1. GitHub → ваш аватар → **Settings** → **Developer settings** → **OAuth Apps** → **New OAuth App**.
2. Заполните:
   - **Application name:** `Админка kendo-baikal.ru` (это увидят редакторы при первом входе);
   - **Homepage URL:** `https://kendo-baikal.ru`;
   - **Authorization callback URL:** `https://kendo-baikal.ru/oauth/callback` (точно так, без пробелов и слэша в конце);
   - **Enable Device Flow** — не включать.
3. **Register application**. На открывшейся странице скопируйте **Client ID** (виден сразу).
4. Нажмите **Generate a new client secret** и сразу скопируйте **Client secret** — потом он не показывается (можно создать новый). Секрет — как пароль: никому не отправляйте, в репозиторий не кладите.

### Шаг 2. Создайте файл с настройками на VPS

Секреты хранятся **только на сервере**, в файле `/var/www/kendo-baikal/.env.oauth`. В репозитории лежит лишь шаблон без значений (`.env.oauth.example`).

```bash
cd /var/www/kendo-baikal
curl -fsSLO https://raw.githubusercontent.com/tulubyev/kendo-baikal/main/.env.oauth.example
umask 077                      # файл будет доступен только вам
cp .env.oauth.example .env.oauth
nano .env.oauth                # впишите значения, см. ниже
chmod 600 .env.oauth
ls -l .env.oauth               # должно быть: -rw------- … .env.oauth
```
В файле:
- `GITHUB_CLIENT_ID=` и `GITHUB_CLIENT_SECRET=` — из шага 1;
- `COOKIE_SECRET=` — случайная строка. Сгенерируйте командой `openssl rand -hex 32` и вставьте результат (64 символа);
- `ALLOWED_USERS=` — логины GitHub через запятую, **включая ваш**: `tulubyev,ivanov,petrova`. Регистр не важен. Пусто — не пустит никого.

Без кавычек и пробелов вокруг `=`. После правки файла примените настройки: `bash deploy.sh` (или `docker compose -f docker-compose.prod.yml --profile oauth up -d --force-recreate kendo-baikal-oauth`).

### Как добавить редактора

1. GitHub → репозиторий `tulubyev/kendo-baikal` → **Settings** → **Collaborators** → **Add people** → логин → роль **Write**. Человек принимает приглашение.
2. На VPS добавьте логин в `ALLOWED_USERS` в `.env.oauth` (`nano .env.oauth`) и примените: `docker compose -f docker-compose.prod.yml --profile oauth up -d --force-recreate kendo-baikal-oauth`.
3. Скажите человеку открыть https://kendo-baikal.ru/admin/ и нажать «Войти через GitHub».

Нужны **оба** условия: логин в `ALLOWED_USERS` (иначе прокси не отдаст токен) и роль Write (иначе GitHub не даст сохранить правки).

### Как убрать редактора

1. Уберите логин из `ALLOWED_USERS` и примените настройки (команда выше) — новые входы прекратятся.
2. **Settings** → **Collaborators** → **Remove** рядом с человеком — это главное: уже выданный токен перестаёт работать на запись сразу.
3. Токен, выданный через вход GitHub, действует, пока человек сам не отзовёт его (GitHub → Settings → Applications → Authorized OAuth Apps → Revoke) или вы не удалите его доступ к репозиторию. Чтобы отозвать у всех сразу — в настройках OAuth-приложения **Revoke all user tokens**.

### Шаг 3. Включите защиту ветки `main` (чтобы без вашего одобрения ничего не публиковалось)

Админка в режиме редакционного процесса создаёт pull request на каждую правку, но **сама по себе не запрещает** редактору нажать «Опубликовать»: слияние делает GitHub от имени редактора, у которого есть право Write. Запретить это может только защита ветки.

1. Репозиторий → **Settings** → **Rules** → **Rulesets** → **New ruleset** → **New branch ruleset**.
2. **Ruleset name:** `Защита main`. **Enforcement status:** **Active**.
3. **Bypass list** → **Add bypass** → выберите **Repository admin** (роль) или лично себя, режим **Always**. Это даёт вам обходить правила — см. ниже.
4. **Target branches** → **Add target** → **Include default branch**.
5. Включите правила:
   - **Require a pull request before merging** → *Required approvals*: **1**;
   - **Require status checks to pass** → **Add checks** → найдите **`verify`** (если в списке пусто — сначала откройте любой PR, чтобы проверка выполнилась хоть раз) — так на сайт не попадёт запись, ломающая сборку;
   - **Block force pushes** и **Restrict deletions** — оставьте включёнными (по умолчанию).
6. **Create**.

Что получается:
- **Редактор** (Write, не в списке обхода) отправил запись «На рассмотрение» → в админке «Опубликовать» ему откажет: GitHub требует одно одобрение и зелёную проверку `verify`.
- **Вы одобряете и публикуете одним из двух способов:**
  - *В админке (проще всего):* войдите, откройте **Редакционный процесс** → карточка в колонке «На рассмотрении» → откройте запись, посмотрите изменения → **«Опубликовать запись»**. Вы в списке обхода, поэтому слияние пройдёт.
  - *На GitHub:* репозиторий → **Pull requests** → ветка вида `cms/posts/…` → **Files changed** → **Review changes** → **Approve** → **Squash and merge** (после зелёной проверки).
- **Свои правки.** Автор pull request не может одобрить его сам (правило GitHub), поэтому без обхода вы застряли бы на собственных записях. Благодаря записи в Bypass list вы просто нажимаете **«Опубликовать»** в админке, а GitHub пропускает слияние без чужого одобрения. Если решите не вносить себя в обход, понадобится второй человек с правом Write, который одобряет ваши правки.
- **Отказ от записи.** Чтобы отклонить правку — в админке «Отбросить изменения» у записи, либо на GitHub закройте pull request (ветка удалится).

> Пока защита ветки **не включена**, любой коллаборатор с ролью Write может сам нажать «Опубликовать», и его правка сразу попадёт на сайт. Включите защиту до того, как позовёте редакторов.

### Как проверить, что всё работает

1. `curl https://kendo-baikal.ru/oauth/healthz` → `ok`.
2. Откройте https://kendo-baikal.ru/admin/ (лучше в окне инкогнито) → **Войти через GitHub** → войдите своим аккаунтом (он есть в `ALLOWED_USERS`) → попадаете в админку.
3. Создайте тестовую запись с включённым переключателем **Черновик** → **Сохранить** → на GitHub появилась ветка `cms/posts/…` и pull request с меткой `sveltia-cms/draft`.
4. Отправьте на рассмотрение → метка сменилась на `sveltia-cms/pending_review`. Опубликуйте → PR слит в `main`, пошла сборка (вкладка Actions).
5. Проверка отказа: войдите вторым GitHub-аккаунтом, которого **нет** в `ALLOWED_USERS` → окно с текстом «Доступ запрещён», в админку не пускает.
6. Проверка защиты ветки: вторым аккаунтом (роль Write, в `ALLOWED_USERS`, не в обходе) создайте запись, отправьте на рассмотрение и нажмите «Опубликовать» → «Не удалось опубликовать запись».
7. Тестовую запись потом удалите (в админке «Удалить» → ещё одна публикация, или удалите файл на GitHub).

Логи прокси: `docker logs --tail 50 kendo-baikal-oauth` (в них логины и статусы, но никогда не токены и не коды).

### Как откатиться

- **Остаться на входе по токену, но с редакционным процессом** — ничего не ломая: просто не пользуйтесь кнопкой GitHub. Кнопка токена остаётся.
- **Отключить прокси:** на VPS `docker compose -f docker-compose.prod.yml --profile oauth stop kendo-baikal-oauth`; чтобы деплой его больше не поднимал — переименуйте `.env.oauth` (`mv .env.oauth .env.oauth.off`). Вход по токену продолжит работать.
- **Вернуть прямые коммиты в `main` без проверки:** в `public/admin/config.yml` замените `publish_mode: editorial_workflow` на `publish_mode: simple` (и при желании уберите три строки `base_url`, `auth_endpoint`, `auth_scope`), слейте в `main`. Не забудьте снять/ослабить защиту ветки, иначе прямые коммиты редакторов упрутся в запрет. Незавершённые pull request'ы `cms/…` закройте на GitHub.
- **Отозвать ключи:** GitHub → Developer settings → OAuth Apps → ваше приложение → **Delete** (или Revoke all user tokens). Смените `GITHUB_CLIENT_SECRET`/`COOKIE_SECRET` в `.env.oauth` и примените настройки.

### Безопасность — важно знать

- Роль **Write** даёт право менять **любой файл** репозитория, включая `Dockerfile`, workflow GitHub Actions и конфиг nginx. Эти файлы собираются и выкатываются на VPS автоматически. Защита ветки `main` с обязательным одобрением (шаг 3) закрывает и этот риск: чужой pull request не попадёт в `main` без вас. Приглашайте только тех, кому доверяете как соавтору сайта.
- **Область доступа токена.** OAuth-приложение GitHub выдаёт токен с правом `public_repo`: он даёт запись во **все публичные репозитории, где у человека есть право записи**, а не только в этот (ограничить область одним репозиторием OAuth-приложение не умеет — это свойство GitHub, не нашей настройки). Токен живёт только в браузере редактора; прокси его не хранит. Поэтому редакторам стоит включить двухфакторную защиту и выходить из админки на чужих компьютерах.
- Прокси пускает только логины из `ALLOWED_USERS`; токен постороннего он не отдаёт и сразу отзывает. Вход защищён от подделки (подписанный одноразовый `state` на 10 минут, привязанный к cookie), число попыток ограничено.
- `.env.oauth` на VPS — `chmod 600`, не копировать в чаты и репозиторий. Утекли `GITHUB_CLIENT_SECRET` — сгенерируйте новый в настройках OAuth-приложения и замените в файле.
- На VPS ограниченный SSH-ключ умеет только запускать `deploy.sh` (см. `DEPLOY.md`). `deploy.sh`, `docker-compose.prod.yml` и `.env.oauth` на сервере лежат копией — **они не обновляются из репозитория автоматически**, правка в репозитории на сервер сама не попадёт.
- Админка не индексируется поисковиками (`noindex`, `X-Robots-Tag`) и не содержит секретов: токен хранится только в браузере редактора.
- Репозиторий публичный: **не загружайте** в админку то, что не должно быть публичным (личные данные, документы с паспортными данными и т. п.) — все загруженные файлы, ветки pull request'ов и вся история видны всем, даже до публикации.

### Что не проверено вживую

Авторы конфигурации не могли открыть админку в браузере с реальным репозиторием и реальным GitHub. Протокол входа сверен по исходникам Sveltia CMS 0.229.0 и проверен автотестами с имитацией GitHub (`oauth/test/`), но после первого развёртывания проверьте по чек-листу «Как проверить» выше, а также: загрузку картинки в записи, правку вложенной страницы (`pages`, адрес вида `club/history`), отсутствие ошибок CSP во вкладке Network/Console браузера. При блокировках CSP расширьте `location /admin/` в `nginx.conf`. Если всплывающее окно входа не связывается с админкой (в консоли — ошибки про `window.opener`), проверьте, что заголовки ответов GitHub/прокси не включают `Cross-Origin-Opener-Policy: same-origin` (у нашего прокси его нет).
